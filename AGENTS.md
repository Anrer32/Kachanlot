# Правила разработки Kachanlot и модуля Ирландии

Эти правила действуют для всего репозитория. Явные указания пользователя имеют
приоритет. Работать в существующем checkout: облачная задача уже изолирована;
не создавать worktree без запроса пользователя.

## Контекст и границы работ

- Цель IRE — самостоятельный модуль качества DLC для HOI4 **1.19.4.1** внутри
  Kachanlot, а не отдельная игра и не официальное дополнение Paradox.
- Прочитать [аудит](docs/IRE_AUDIT.md) и
  [план реализации](docs/IRE_IMPLEMENTATION_PLAN.md) до работы над IRE.
  Аудит описывает найденное, план — будущие решения. Сверять их с текущими файлами.
- **Историческая база пока не утверждена. Не создавать фокусы, идеи, их игровые
  заглушки или стартовые эффекты до явного утверждения пользователем.** Сначала
  подготовить исторический dossier и зафиксировать утверждённую ревизию, дату и
  границы утверждения в документации. Аудит и архитектура сами по себе не approval.
- В задачах на документацию менять только согласованные Markdown-файлы.
  Не менять `common/`, `history/`, `events/`, `localisation/`, `interface/`, `gfx/`,
  `map/`, descriptor, существующие сценарии и баланс «заодно».
- Не заполнять пробелы историческими догадками. Различать факт с источником,
  проектное решение, альтернативную историю и непроверенное предположение.

## Сохранность и управление изменениями

- До работы проверить `git status --short`, ветку и локальные инструкции;
  сохранять чужие изменения. Не reset, не force push, не пересоздавать старые коммиты.
- Использовать отдельную ветку и небольшие тематические PR. Если аудит ещё не в
  целевой ветке, использовать зависимый PR с явно указанной базой: diff новой
  архитектуры не должен повторять аудит. Не выполнять merge и публикацию среды
  или Workshop без соответствующего запроса.
- Не считать локальный commit, push, открытый PR, запуск игры и публикацию одним
  действием. Сообщать только о подтверждённых результатах; при отказе API оставить
  готовую ветку/описание и точно назвать блокер.
- Изменение history/одноимённого vanilla-файла — отдельное обоснованное решение.
  Сначала проверить оригинал 1.19.4.1 и DLC, сохранить полный обязательный контекст.
  Не создавать второй файл с тем же объектом ради мнимого «дополнения» первого.
- Не добавлять широкие `replace_path`, новый тег IRE или глобальные правила ради
  локальной задачи. Не копировать в Git установку игры, DLC, saves, логи с личными
  данными и чужую графику без прав. Не выводить секреты и не сохранять их в файлы.

## Контракты реализации после утверждения базы

- Новые собственные ID используют `IRE_KLN_` и типизированные имена из раздела 4
  плана. Реестр ID обязателен до добавления определения. Префикс не гарантирует
  уникальность: искать коллизии также в vanilla/DLC.
- Существующие vanilla ID не переименовывать и не дублировать; ссылки на них
  регистрировать как внешние. Старые четыре ключа локализации IRE — зарезервированные
  legacy-ключи, а не разрешение создать четыре духа без исторического решения.
- Системные ключи движка, country tags, числовые state/province ID и `GFX_*`
  подчиняются формату движка; не навязывать им недопустимые имена ради префикса.
- Единственный инициализатор IRE работает в country scope; не повторяет награды,
  не возвращает снятые духи после load и не запускается у всех стран.
  Новый старт, миграция save, освобождение и гражданская война — разные сценарии.
- Отделять данные/историю от эффектов: решения, фокусы и события вызывают общие
  переходы состояния, а не независимо переписывают одни и те же флаги и бонусы.
- Локализация не определяет и не выдаёт идею. Видимый spirit, hidden modifier,
  экономический закон и нанимаемый советник — разные сущности.
- Учитывать законы `_economic.txt` / `_manpower.txt`, нефтяной эффект, host tool,
  новые доктрины/технологии/фракции и существующий ENG/GER-контент. Не менять чужие
  переменные и не полагаться на порядок загрузки on-actions.
- Делать адресные события и ограниченные пульсы. Не вводить глобальный ежедневный
  опрос ради IRE. Каждой механике нужны диапазоны, ограничения бонусов и исходы отказа.
- Для каждой DLC-зависимости зафиксировать проверенный fallback либо явно
  неподдерживаемый набор. Не придумывать гарантии совместимости.
- Сохранять UTF-8 BOM у игровых локализаций, заголовок языка и формат HOI4.
  Для русских строк обеспечивать английскую пару, полный `_desc`/tooltip и
  согласованные GFX-ссылки. Markdown — обычный UTF-8.

## Проверка и отчётность

- Для документации достаточно проверки diff, локальных ссылок и состава файлов;
  не запускать игровые тесты и не устанавливать зависимости без необходимости.
- Для игровых изменений необходимы уровни L1–L4 из плана: структура/кодировка,
  контекстные ссылки и ID, синтаксис с учётом версии, затем реальная игра.
  Проверка скобок или обычный YAML parser не заменяет парсер HOI4.
- Тест выдачи духа обязан показать естественный путь старта, `has_idea` у IRE,
  отсутствие ошибочной выдачи другим странам, отображение и численное действие;
  после снятия/реформы и save/load бонус не должен возвращаться или удваиваться.
- Сохранять baseline ошибок Kachanlot отдельно от новых ошибок. Отмечать passed,
  failed, skipped, blocked и not run; не выдавать отсутствие тестов за прохождение.
- Без запуска HOI4 не писать «мод работает», «ветка готова в игре», «совместим со
  всеми DLC». Указывать commit, версию игры, DLC, сценарий и фактические результаты.

## Завершение этапа

Проверить `git diff --check` и состав diff, сохранить документацию проверки.
В PR указать конкретный результат, область изменений, зависимости от предыдущих
PR, выполненные проверки и что требует игры/источников. Остановить расширение
этапа после достижения его критериев; следующий этап не подразумевается автоматически.
